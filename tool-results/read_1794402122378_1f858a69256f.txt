     1→# ATLAS — System Architecture
     2→
     3→> **ATLAS** = *Autonomous Technical Limit Assessment System*.
     4→> A Next.js 16 dashboard that monitors and visualizes AI agent capabilities,
     5→> limits, and benchmark performance for a registered sandbox runtime.
     6→> The product is also the test: the dashboard is built *inside* the very
     7→> sandbox it observes, and its own seed data and live-benchmark results are
     8→> the artifacts that prove the agent's environment behaves the way the
     9→> dashboard claims it does.
    10→
    11→---
    12→
    13→## 1. Overview
    14→
    15→ATLAS is a single-page Next.js 16 (App Router) application that ships as a
    16→self-contained dashboard for "agent capability telemetry." The frontend is a
    17→Zustand-driven, six-view SPA that lives entirely at `/`. The backend is a set
    18→of Next.js Route Handlers under `/api/*` that talk to a local SQLite database
    19→through Prisma 6. A small but important extra surface is the **live benchmark
    20→subprocess** — `POST /api/benchmarks/run` spawns `python3 -c <script>` with a
    21→30-second timeout, parses the printed `perf_counter` duration, and persists
    22→the result as a `BenchmarkRun` row. That single endpoint is what makes ATLAS
    23→*both* the test (it produces real telemetry by running real code) and the
    24→product (it visualizes that telemetry with charts, tables, and gauges).
    25→
    26→The architectural posture is deliberately conservative: no auth, no external
    27→caching layer, no message queue, no server-side rendering beyond the shell.
    28→React Query 5 is the cache. Zustand 5 is the only client state store. Tailwind
    29→CSS 4 with shadcn/ui (New York variant) provides the design system. Charts are
    30→recharts 2. Animations are framer-motion 12. The theme is light/dark via
    31→`next-themes`. The whole stack is small, mainstream, and verifiable by a single
    32→human or agent reading the source in an afternoon.
    33→
    34→The project was developed in a **kata-container** sandbox (Debian 13 trixie,
    35→2-vCPU Intel Xeon, 4.1 GiB RAM, 0 swap, egress IP 8.212.10.159). All env values
    36→in the seed data — Node 24.22.2, Bun 1.3.14, Python 3.12.16, gcc 14.2, git
    37→2.47.3, the absence of rust/go/ruby/php/docker/gh — are real probe outputs,
    38→captured live and persisted to `docs/environment/` and `seed-data/benchmarks.json`.
    39→The dashboard therefore documents its own host, recursively.

    91→## 3. Data flow — read path
    92→
    93→```mermaid
    94→sequenceDiagram
    95→  actor U as User
    96→  participant Shell as AtlasApp
    97→  participant Z as view-store (Zustand)
    98→  participant V as DashboardView
    99→  participant RQ as React Query
   100→  participant API as /api/stats
   101→  participant DB as Prisma → SQLite
   102→
   103→  U->>Shell: clicks sidebar item
   104→  Shell->>Z: setView("dashboard")
   105→  Z-->>Shell: view === "dashboard"
   106→  Shell->>V: render <DashboardView/>
   107→  V->>RQ: useStats() — queryKey ["atlas","stats"]
   108→  RQ->>API: GET /api/stats (cache: no-store)
   109→  API->>DB: db.environment.count() + 6 more<br/>(Promise.all)
   110→  DB-->>API: 7 integer counts + lastRun + avg
   111→  API-->>RQ: 200 { environments, tools, … }
   112→  RQ-->>V: data / isLoading / isError
   113→  V->>V: render StatCards + charts
   114→  V-->>U: painted dashboard
   115→```
   116→
   117→This read path is followed by every view, with only the query hooks
   118→differing. The `apiGet` helper in `src/lib/api.ts` always sets
   119→`cache: "no-store"` (because React Query owns caching) and Accepts JSON. The
   120→backend returns the *exact* shape the type expects, validated structurally by
   121→the `src/types/atlas.ts` interfaces and at-runtime by the server-side Zod
   122→schemas in each Route Handler.
   123→
   124→The pagination envelope — `{ data, total, page, limit }` — is the same across
   125→all list endpoints (`/api/tools`, `/api/capabilities`, `/api/limits`,
   126→`/api/reports`, `/api/benchmarks` returns `{ data, total }` since it is not
   127→paginated). Non-paginated single-object responses are wrapped as `{ data: obj }`
   128→(`GET /api/environments?id=…`, `GET /api/benchmarks/[id]`,
   129→`POST /api/benchmarks/run`, `POST /api/reports`). This consistent envelope
   130→makes the React Query hooks simple: a single `unwrap` step handles either
   131→shape.

   135→## 4. Live benchmark run — write path
   136→
   137→```mermaid
   138→sequenceDiagram
   139→  actor U as User
   140→  participant V as BenchmarksView
   141→  participant RQ as React Query mutation
   142→  participant API as POST /api/benchmarks/run
   143→  participant Py as python3 -c <script>
   144→  participant DB as Prisma → SQLite
   145→
   146→  U->>V: selects "fib_recursive_30", clicks Run
   147→  V->>RQ: useRunBenchmark().mutate({name})
   148→  RQ->>API: POST { name: "fib_recursive_30" }
   149→  API->>API: Zod bodySchema.safeParse(body)
   150→  API->>API: BENCH_PYTHON[name] lookup
   151→  API->>Py: execFileP("python3", ["-c", script], { timeout: 30_000, maxBuffer: 10MB })
   152→  Note over Py: time.perf_counter()<br/>fib(30)<br/>print(f"{(e-s)*1000:.3f}")
   153→  Py-->>API: stdout "122.778\n"
   154→  API->>API: parseFloat(stdout.split('\n').last)
   155→  API->>DB: db.benchmark.findUnique({name}) or create
   156→  API->>DB: db.environment.findFirst() — single-tenant
   157→  API->>DB: db.benchmarkRun.create({ benchmarkId, environmentId, durationMs, success, details })
   158→  DB-->>API: created row with includes
   159→  API-->>RQ: 201 { data: BenchmarkRun }
   160→  RQ->>RQ: qc.invalidateQueries(["atlas","benchmarks"])<br/>qc.invalidateQueries(["atlas","stats"])
   161→  RQ-->>V: onSuccess → setLastResult + sonner.toast
   162→  V-->>U: green result card "122.78 ms"
   163→```
   164→
   165→The supported benchmarks are an enum-like set defined in the route's
   166→`BENCH_PYTHON` record: `csv_generate_1m`, `sha256_10k`, `fib_recursive_30`,
   167→`matmul_100x100`. Any other `name` is rejected with 400 `unsupported_benchmark`
   168→and the response includes a `supported` list. The 30-second timeout is a hard
   169→cap enforced by Node's `child_process.execFile`; if the script exceeds it, the
   170→catch block returns 500 `benchmark_execution_failed` with the stderr attached.
   171→
   172→> **Serverless caveat.** The endpoint uses `child_process.execFile('python3',
   173→> …)`, which requires the runtime to have a `python3` binary *and* the right to
   174→> spawn child processes. On Vercel's default serverless runtime this endpoint
   175→> will fail (no `python3` in the function image). The local-dev sandbox and a
   176→> self-hosted Caddy-fronted deployment both work. The production strategy is
   177→> documented in `docs/decisions/adr-11-live-benchmark-subprocess.md`.

   181→## 5. Database ERD
   182→
   183→The Prisma schema declares **7 models** with cuid IDs on SQLite. Relations
   184→cascade-delete from `Environment` down to its children, so deleting an
   185→environment wipes its tools, capabilities, limits, and benchmark runs in one
   186→transaction.
   187→
   188→```mermaid
   189→erDiagram
   190→  Environment ||--o{ Tool : "has"
   191→  Environment ||--o{ Capability : "measures"
   192→  Environment ||--o{ BenchmarkRun : "runs on"
   193→  Environment ||--o{ Limit : "imposes"
   194→  Benchmark ||--o{ BenchmarkRun : "produces"
   195→
   196→  Environment {
   197→    string id PK "cuid"
   198→    string hostname
   199→    string osName
   200→    string osVersion
   201→    string kernel
   202→    string cpuModel
   203→    int cpuCores
   204→    int memoryMb
   205→    int swapMb "default 0"
   206→    int diskGb "default 0"
   207→    string container
   208→    string publicIp
   209→    string arch
   210→    datetime createdAt
   211→  }
   212→
   213→  Tool {
   214→    string id PK "cuid"
   215→    string name
   216→    string category
   217→    string version
   218→    string path
   219→    boolean installed "default true"
   220→    string environmentId FK
   221→    datetime createdAt
   222→  }
   223→
   224→  Capability {
   225→    string id PK "cuid"
   226→    string environmentId FK
   227→    string category
   228→    string name
   229→    float value
   230→    string unit
   231→    string details
   232→    datetime createdAt
   233→  }
   234→
   235→  Benchmark {
   236→    string id PK "cuid"
   237→    string name UK
   238→    string category
   239→    string description
   240→    string unit
   241→  }
   242→
   243→  BenchmarkRun {
   244→    string id PK "cuid"
   245→    string benchmarkId FK
   246→    string environmentId FK
   247→    float durationMs
   248→    string throughput "nullable"
   249→    boolean success "default true"
   250→    string details "nullable"
   251→    datetime createdAt
   252→  }
   253→
   254→  Limit {
   255→    string id PK "cuid"
   256→    string environmentId FK
   257→    string resource
   258→    string limitValue
   259→    string unit
   260→    string kind
   261→    string details
   262→    string severity "default info"
   263→    datetime createdAt
   264→  }
   265→
   266→  Report {
   267→    string id PK "cuid"
   268→    string title
   269→    string format
   270→    string parameters "JSON-encoded"
   271→    string content
   272→    datetime createdAt
   273→  }
   274→```
   275→
   276→`Report` is intentionally standalone — it has no FK to anything. A report is a
   277→point-in-time snapshot of the dataset, persisted as a single string of HTML,
   278→JSON, or CSV. The `parameters` column stores the JSON-encoded parameters object
   279→the caller passed in (`{"include":["stats","benchmarks","limits"],…}`) so the
   280→report is self-describing.
   281→
   282→The seed data populates: **1** environment, **28** tools (20 installed + 8
   283→not-installed), **15** capabilities (5 measured + 10 mirrored benchmark
   284→durations), **10** benchmarks, **10** benchmark runs, **10** limits, **0**
   285→reports. See `prisma/seed.ts` for the exact values and `seed-data/benchmarks.json`
   286→for the validated benchmark results.

   290→## 6. API flow — request/response shape
   291→
   292→Every Route Handler follows the same pattern:
   293→
   294→```mermaid
   295→flowchart TB
   296→  Req["Incoming Request"] --> Parse[Parse query string or JSON body]
   297→  Parse -->|query| ZodQ[zod querySchema.safeParse]
   298→  Parse -->|body| ZodB[zod bodySchema.safeParse]
   299→  ZodQ -->|fail| Err400[400 { error: 'invalid_query', details: zod.issues }]
   300→  ZodB -->|fail| Err400B[400 { error: 'invalid_body' or 'invalid_json_body', details }]
   301→  ZodQ -->|ok| Prisma[(Prisma findMany / count / aggregate)]
   302→  ZodB -->|ok| SideFx[Side effects: child_process, db.create, ...]
   303→  SideFx --> Prisma
   304→  Prisma --> Envelope[Wrap result: { data, total, page, limit } or { data }]
   305→  Envelope --> Res200[200 / 201 JSON response]
   306→  Prisma -.->|throws| Err500[500 { error: 'failed_to_X', details: err.message }]
   307→  Err400 --> Res
   308→  Err400B --> Res
   309→  Err500 --> Res
   310→  Res200 --> Res["NextResponse.json(...)"]
   311→```
   312→
   313→The error shape is consistent everywhere:
   314→
   315→```jsonc
   316→// 400 / 404 / 500
   317→{
   318→  "error": "snake_case_machine_code",     // stable identifier for client switch
   319→  "details": "human-readable string OR zod.issues array",  // optional
   320→  "supported": ["csv_generate_1m", "..."], // optional, only on POST /api/benchmarks/run
   321→  "stderr": "..."                          // optional, only on benchmark run failures
   322→}
   323→```
   324→
   325→The client-side `apiGet`/`apiPost` helpers in `src/lib/api.ts` unwrap this
   326→shape and throw a typed `ApiError` with `.status` and `.body`, which React
   327→Query then surfaces as `isError` / `error.message` to the views. The
   328→`ErrorState` component renders the message and offers a Retry button that
   329→re-invokes the query.

   333→## 7. Deployment topology
   334→
   335→```mermaid
   336→flowchart LR
   337→  Dev["Developer machine<br/>(Debian 13 sandbox)"] -- "git push" --> GitHub["github.com/AutomatedLabor/atlas"]
   338→  GitHub -- "auto-deploy on push to main" --> VercelBuild["Vercel Build<br/>(next build)"]
   339→  VercelBuild -- "output: .next/standalone" --> VercelFn["Vercel Serverless Functions<br/>(Node 20+ runtime)"]
   340→  VercelFn -- "each Route Handler" --> PrismaProd["Prisma Client"]
   341→  subgraph DBLayer["Data layer"]
   342→    SQLiteDev[("SQLite<br/>db/custom.db")]
   343→    PostgresProd[("Postgres<br/>(recommended for prod)")]
   344→  end
   345→  PrismaProd --> SQLiteDev
   346→  PrismaProd -. "via DATABASE_URL env swap" .-> PostgresProd
   347→  VercelFn -- "POST /api/benchmarks/run<br/>(spawns python3)" .->|"FAILS on serverless"| Known["Known limitation<br/>(see adr-11)"]
   348→  Browser["Browser"] -- "HTTPS" --> VercelFn
   349→```
   350→
   351→The project ships with `next.config.ts` set to `output: "standalone"`, which
   352→produces a self-contained `.next/standalone/server.js` that can run on any
   353→Node 20+ host. The `bun run build` script additionally copies `.next/static`
   354→and `public/` into `.next/standalone/` so the standalone server can serve
   355→static assets without an external CDN.
   356→
   357→The Prisma schema is **Postgres-ready** — only the `datasource` block of
   358→`prisma/schema.prisma` needs to change for production:
   359→
   360→```prisma
   361→datasource db {
   362→  provider = "postgresql"      // was "sqlite"
   363→  url      = env("DATABASE_URL") // was file:…/custom.db, now postgres://…
   364→}
   365→```
   366→
   367→No model changes are required; `cuid()` IDs, `DateTime` fields, and all
   368→relation decorators work identically on both providers. See
   369→`docs/decisions/adr-02-prisma-sqlite.md` for the trade-off discussion and
   370→`docs/deployment-guide.md` for step-by-step Vercel deployment.
   371→
   372→> **SQLite-on-serverless caveat.** A SQLite file is a single local file; on
   373→> Vercel, the function filesystem is ephemeral and read-only (except `/tmp`).
   374→> Seeding writes to the file, then a new invocation starts in a fresh
   375→> container and sees the seed from the build phase — but writes during runtime
   376→> (e.g., `POST /api/benchmarks/run`) will not persist across cold starts. For
   377→> production, switch the `DATABASE_URL` to Vercel Postgres or Turso (SQLite
   378→> over the network). The schema is identical; only the URL changes.

   505→## 10. State management — three tiers
   506→
   507→ATLAS uses three different state mechanisms, kept deliberately orthogonal:
   508→
   509→1. **Server state** — React Query 5. Every hook in `src/hooks/atlas/index.ts`
   510→   wraps a `useQuery` or `useMutation`. The `QueryClient` is created once in
   511→   `src/lib/query-provider.tsx` with `staleTime: 30_000`, `refetchOnWindowFocus:
   512→   false`, `retry: 1`. After every successful mutation, the mutation's
   513→   `onSuccess` calls `qc.invalidateQueries({ queryKey: ["atlas", ...] })` so
   514→   dependent views refetch from the server.
   515→
   516→2. **Client UI state** — Zustand 5. `src/lib/view-store.ts` exports two
   517→   stores: `useViewStore` (the active `AtlasView`) and `useNotificationPrefs`
   518→   (three toast toggles). No Zustand middleware; no persistence; the state is
   519→   purely in-memory and resets on reload.
   520→
   521→3. **Local UI state** — `useState` inside views. Search filters, slider
   522→   values, dialog open/close, selected benchmark id, etc. are kept local to
   523→   the component that owns them. This keeps prop drilling shallow and means a
   524→   view unmount cleanly resets its filters when the user switches tabs.
   525→
   526→There is no Redux, no Jotai, no Recoil, no MobX, and no React Context
   527→provider chain. The provider tree is exactly three levels deep:
   528→`ThemeProvider → QueryProvider → {children}`.

   550→## 12. Build & run topology
   551→
   552→| Concern | Choice | Where it's configured |
   553→|---------|--------|----------------------|
   554→| Package manager | Bun 1.3 (lockfile `bun.lock`); `npm`/`pnpm` also work | `bun.lock` |
   555→| Dev server | `next dev -p 3000`, piped through `tee dev.log` | `package.json` `scripts.dev` |
   556→| Build | `next build` + copy `.next/static` and `public/` into `.next/standalone/` | `package.json` `scripts.build` |
   557→| Prod server | `bun .next/standalone/server.js` (NODE_ENV=production) | `package.json` `scripts.start` |
   558→| Lint | `eslint .` (next core-web-vitals + typescript, many rules relaxed) | `eslint.config.mjs` |
   559→| Type check | `bunx tsc --noEmit` (strict, noEmit, `@/*` alias) | `tsconfig.json` |
   560→| DB schema | `prisma db push --accept-data-loss` (dev only — no migration history) | `package.json` `scripts.db:push` |
   561→| DB generate | `prisma generate` (regenerates the client after schema changes) | `package.json` `scripts.db:generate` |
   562→| Seed | `bun run prisma/seed.ts` (idempotent: wipes all rows then inserts) | `prisma/seed.ts` |
   563→| Standalone | `output: "standalone"` + `serverExternalPackages: ["@prisma/client", ".prisma/client"]` | `next.config.ts` |
   564→
   565→The `serverExternalPackages` entry is essential: Prisma ships native `.node`
   566→bindings that Turbopack/Webpack cannot bundle. Marking the package external
   567→tells Next to load it via `require()` at runtime from `node_modules`, which
   568→preserves the binary.

   572→## 13. Architectural trade-offs (honest summary)
   573→
   574→| Decision | Win | Cost |
   575→|----------|-----|------|
   576→| Single `/` route with Zustand switching | Instant view swaps, no router plumbing, no SSR-per-view | No deep linking, no per-view code splitting without `React.lazy`, browser back button does nothing |
   577→| SQLite for dev | Zero-config, file-based, `prisma db push` is one line | Serverless production needs Postgres or Turso; the `DATABASE_URL` swap is the only change |
   578→| `python3 -c` subprocess for live benchmarks | Real timing, language-agnostic, isolated | Will not run on Vercel serverless (no python3, no fork right); needs a worker for prod |
   579→| No auth in v1 | Trivially readable, all GET endpoints open, easy local dev | Anyone with the URL can POST a benchmark run; documented in `security.md` and ADR-06 |
   580→| recharts 2 for charts | Declarative, well-documented, responsive | Bundle is non-trivial (~150 KB gzipped); mitigated by tree-shaking named imports |
   581→| Tailwind 4 + shadcn/ui New York | Owned components, semantic tokens, dark mode trivial | Generated primitives require occasional manual updates; not as theme-rich as MUI |
   582→| React Query 5 | Caching, dedup, devtools, mutation invalidation | Adds ~40 KB; one more library to upgrade |
   583→| Zustand 5 for view state | 4-line store, no provider | No persistence; reload resets to "dashboard" |
   584→
   585→Each of these is expanded in `docs/decisions/`. The unifying theme is
   586→**small, mainstream, verifiable**. The whole app is a few thousand lines of
   587→TypeScript plus a few hundred lines of SQL DDL via Prisma. A reviewer with
   588→Next.js experience can hold the entire architecture in their head.
