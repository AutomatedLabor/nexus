     1→# ATLAS — Security
     2→
     3→ATLAS is a **read-heavy** dashboard with a small number of write endpoints
     4→(`POST /api/benchmarks/run`, `POST /api/reports`, and the download `GET
     5→/api/export`). The most sensitive threat surfaces are: (a) the live
     6→benchmark subprocess, which spawns a Python interpreter on every request;
     7→(b) report content, which is persisted to the database and rendered back to
     8→the user; (c) the export endpoint, which can exfiltrate the full dataset;
     9→and (d) the absence of authentication, which is currently by design and
    10→documented here as a deliberate v1 gap with a remediation plan.
    11→
    12→This document is the **threat model**, the **security measures in place**,
    13→the **measures missing**, and the **incident response plan**.
    14→
    15→---
    16→
    17→## 1. Threat model
    18→
    19→### 1.1 What ATLAS is
    20→
    21→ATLAS is a single-page Next.js 16 dashboard that visualizes telemetry about
    22→its own sandbox host: the OS, hardware, installed tools, benchmark
    23→durations, and architectural limits. The seed data includes the public
    24→egress IP (`8.212.10.159`), the hostname, the kernel version, and a list of
    25→which tools are *not* installed (e.g., `no_docker`, `no_rust`). The frontend
    26→exposes all of this in the Environment and Limits views. The data is
    27→**deliberately** displayed — it is the product.
    28→
    29→### 1.2 The asset inventory
    30→
    31→| Asset | Sensitivity | Where it lives | Exposed to |
    32→|-------|-------------|----------------|------------|
    33→| Environment metadata (hostname, kernel, CPU, public IP) | Low — internal telemetry | `Environment` table | Anyone who can reach the dashboard |
    34→| Tool inventory (installed versions, paths) | Low | `Tool` table | Anyone who can reach the dashboard |
    35→| Benchmark durations (real timing data) | Low | `BenchmarkRun` table | Anyone who can reach the dashboard |
    36→| Limits (e.g., "no swap", "0 MB swap", "egress IP 8.212.10.159") | Low — already in `docs/environment/` | `Limit` table | Anyone who can reach the dashboard |
    37→| Report content (HTML/JSON/CSV text the user generated) | Low — copies of the above | `Report.content` column | Anyone who can reach the dashboard |
    38→| User-supplied API keys (Settings → API keys UI) | Medium — but **browser-only**, never sent to the server | `localStorage` only | Anyone with browser access to the same origin |
    39→| `DATABASE_URL` (in `.env` or Vercel) | High | Environment variables | Anyone with deployment access |
    40→| The Prisma `db/custom.db` file (dev) | Medium | Local filesystem | Anyone with read access to the dev machine |
    41→| The prod Postgres connection string | High | Vercel env vars | Anyone with Vercel project access |
    42→
    43→There is **no PII** in any of these. There is no auth, no sessions, no
    44→passwords. The "API keys" in Settings are mock UI stored in `localStorage`
    45→only — the source code is explicit about this (`Settings → API keys`
    46→description reads "Mock — client only.").
    47→
    48→### 1.3 Threat actors
    49→
    50→1. **Unauthenticated internet user** — anyone who can reach the deployed
    51→   URL. Currently, they can read all data and trigger a benchmark run.
    52→2. **Authorized user of the dashboard** — same access as #1 plus the ability
    53→   to use the Settings UI (which only writes to their own browser's
    54→   localStorage).
    55→3. **Deployment operator** — anyone with access to the Vercel project (can
    56→   read env vars including `DATABASE_URL`, can deploy, can rollback).
    57→4. **Database administrator** — anyone with direct access to the Postgres
    58→   instance in prod (can read/write anything in the DB).
    59→5. **Malicious npm/bun dependency** — any installed package could
    60→   theoretically include malicious code that runs at build or runtime.
    61→
    62→### 1.4 Specific threats
    63→
    64→#### T1 — Abusive benchmark runs (CPU DoS)
    65→
    66→`POST /api/benchmarks/run` spawns a Python subprocess that takes 5–300 ms
    67→per call. Without rate limiting, an attacker can hammer the endpoint and
    68→saturate one CPU core (the sandbox has 2). At 100 req/s, the endpoint alone
    69→would consume ~30% of the sandbox's CPU continuously — not a DoS, but a
    70→steady drain. At 1000 req/s, the endpoint becomes the bottleneck.
    71→
    72→**Current mitigation**: the 30-second subprocess timeout caps each request
    73→at 30 s of CPU; combined with the Python GIL, only one subprocess runs at a
    74→time per Node process (Node's `execFile` does not parallelize within a single
    75→process). So the worst case per request is 30 s of CPU, and concurrent
    76→requests are serialized by the Node event loop until `execFile` returns.
    77→
    78→**Gap**: no rate limit. A single attacker could submit 100 concurrent
    79→requests, each waiting up to 30 s, holding the function warm for 30 s.
    80→
    81→#### T2 — Report content injection (XSS)
    82→
    83→`POST /api/reports` accepts a `title` string (`min(1)`, `max(200)`) and an
    84→arbitrary `parameters` object (Zod-validated as `z.record(z.string(),
    85→z.unknown())`). The server then renders `content` in one of three formats:
    86→
    87→- **JSON format**: `JSON.stringify({ stats, runs, limits })`. No injection
    88→  possible — `JSON.stringify` escapes everything correctly.
    89→- **CSV format**: `csvEscape()` wraps and quotes values containing
    90→  `,`, `"`, `\n`, `\r`. The output is CSV-safe; opening it in a spreadsheet
    91→  is safe.
    92→- **HTML format**: a hand-rolled template that escapes the title (`<`, `>`,
    93→  `&`) and the `details` column (`<`, `>`, `&`). Other values (benchmark
    94→  name, category, hostname) are not escaped, but they come from the
    95→  database (seed-controlled) — a user cannot inject into them through the
    96→  report endpoint.
    97→
    98→**Critical question**: does the frontend ever render the HTML-format
    99→report content as live HTML?
   100→
   101→**Answer**: **No**. The Reports view opens a `Dialog` with the report
   102→content in a `<pre>` block (line 285 of
   103→`src/components/atlas/views/reports-view.tsx`):
   104→
   105→```tsx
   106→<pre className="whitespace-pre-wrap break-words p-4 text-xs font-mono text-foreground">
   107→  {openReport?.content ?? "(no content)"}
   108→</pre>
   109→```
   110→
   111→React's JSX escapes text children. There is **no `dangerouslySetInnerHTML`
   112→anywhere in the ATLAS-authored components** — verified by reading every
   113→file under `src/components/atlas/`. The shadcn primitives also don't use
   114→`dangerouslySetInnerHTML` in any path ATLAS exercises.
   115→
   116→**Conclusion**: even if an attacker managed to insert `<script>` into a
   117→report's content (which the endpoint prevents anyway), the frontend would
   118→render it as text, not as live HTML. The XSS surface through reports is
   119→zero.
   120→
   121→#### T3 — Data exfiltration via export
   122→
   123→`GET /api/export?format=csv|json` returns the entire `BenchmarkRun` and
   124→`Limit` tables. In v1, this is fine — the data is non-sensitive and is
   125→already visible in the UI. In a multi-tenant future where the dashboard
   126→holds multiple environments' data, the export endpoint would need to
   127→filter by the caller's authorized environments.
   128→
   129→**Current mitigation**: none beyond same-origin (the endpoint is at
   130→`/api/export`, on the same origin as the dashboard). Cross-origin requests
   131→are blocked by the browser's default CORS policy (no `Access-Control-Allow-
   132→Origin` header is set, so other origins can't read the response).
   133→
   134→#### T4 — Unauthorized API access
   135→
   136→There is **no authentication** on any endpoint. Anyone who can reach the
   137→URL can:
   138→
   139→- Read all data (every `GET` endpoint).
   140→- Create reports (`POST /api/reports`).
   141→- Run benchmarks (`POST /api/benchmarks/run`).
   142→- Trigger exports (`GET /api/export`).
   143→- (Currently can't delete anything — there are no DELETE endpoints.)
   144→
   145→**Current mitigation**: the deploy URL is not advertised. In dev, the
   146→sandbox is on a private network. In prod, Vercel's URL is publicly
   147→discoverable but not indexed.
   148→
   149→**Gap**: full read+write access for anyone who finds the URL. See §4.
   150→
   151→#### T5 — Database corruption / loss
   152→
   153→The dev SQLite file can be deleted or corrupted by any process with write
   154→access to `db/custom.db`. The Prisma seed is idempotent and restores the
   155→canonical state in ~2 s. The prod Postgres has its own backup story
   156→(managed by the provider).
   157→
   158→**Current mitigation**: re-seeding restores the canonical state. User-
   159→generated data (reports, additional benchmark runs) would be lost on
   160→re-seed.
   161→
   162→#### T6 — Malicious dependency
   163→
   164→`bun install` runs `postinstall` scripts for every package. ATLAS depends
   165→on ~60 packages, including `@prisma/client`, `next`, `react`, `recharts`,
   166→`framer-motion`, `lucide-react`, `sonner`, `next-themes`, `zod`, `zustand`,
   167→`z-ai-web-dev-sdk`, `next-auth` (installed but not used in v1), and 50+ shadcn
   168→primitives (each backed by a Radix package). Any of these could in
   169→principle ship malicious code in a version bump.
   170→
   171→**Current mitigation**: none beyond using mainstream, well-maintained
   172→packages. No `npm audit` gate, no SBOM generation, no Sigstore
   173→verification.
   174→
   175→**Gap**: a `bun audit` step in CI would catch known CVEs in dependencies.
   176→See §6.
   177→
   178→#### T7 — Subprocess escape
   179→
   180→The Python subprocess spawned by `POST /api/benchmarks/run` runs as the
   181→same user as the Node process, with the same filesystem permissions. The
   182→scripts are hard-coded in `BENCH_PYTHON` and don't accept any user input
   183→beyond the `name` (which is Zod-validated against the supported set). So
   184→there is no command injection vector.
   185→
   186→But: if an attacker found a way to bypass the `name` validation and
   187→insert arbitrary Python, they could execute arbitrary code on the host.
   188→The 30 s timeout limits the damage but doesn't prevent it.
   189→
   190→**Current mitigation**: `name` is validated by `z.string().min(1)` then
   191→checked against `BENCH_PYTHON[name]`; if not in the map, 400. There is no
   192→way to pass a custom script.
   193→
   194→**Gap**: the `name` validation is `z.string().min(1)` — any non-empty
   195→string passes Zod. The `BENCH_PYTHON[name]` check is the only gate. If a
   196→future refactor accidentally removed the lookup, the endpoint would
   197→still accept any `name`. A tighter Zod schema (`z.enum([...])`) would
   198→catch this at the type level.

   202→## 2. Security measures implemented
   203→
   204→### 2.1 Input validation on every write endpoint
   205→
   206→Every endpoint that accepts user input uses Zod validation:
   207→
   208→| Endpoint | Schema |
   209→|----------|--------|
   210→| `POST /api/benchmarks/run` | `z.object({ name: z.string().min(1) })` |
   211→| `POST /api/reports` | `z.object({ title: z.string().min(1).max(200), format: z.enum(['html','json','csv']), parameters: z.record(z.string(), z.unknown()).optional() })` |
   212→| `GET /api/tools` | `z.object({ q: z.string().optional(), category: z.string().optional(), installed: z.enum(['true','false']).optional(), page: z.coerce.number().int().min(1).default(1), limit: z.coerce.number().int().min(1).max(200).default(50) })` |
   213→| `GET /api/capabilities` | `z.object({ category, environmentId: z.string().optional(), page, limit })` |
   214→| `GET /api/limits` | `z.object({ severity, kind, page, limit })` |
   215→| `GET /api/environments` | `z.object({ id: z.string().optional() })` |
   216→| `GET /api/export` | `z.object({ format: z.enum(['csv','json']).default('json') })` |
   217→
   218→Zod fails produce 400 with `{ error: 'invalid_query' | 'invalid_body',
   219→details: zod.issues[] }`. The shape is documented in `docs/api-reference.md`
   220→§13.
   221→
   222→### 2.2 30-second subprocess timeout
   223→
   224→The benchmark subprocess is spawned with `timeout: 30_000` (and `maxBuffer:
   225→10 * 1024 * 1024`). If the script hangs (e.g., infinite loop), Node kills
   226→it at 30 s and the route returns 500 `benchmark_execution_failed` with
   227→the stderr.
   228→
   229→This is the primary CPU DoS mitigation: a single request can hold at most
   230→30 s of CPU. Combined with Node's single-threaded event loop, the
   231→subprocess serializes concurrent requests — they wait in the event loop
   232→until the previous `execFile` returns.
   233→
   234→### 2.3 Pagination caps
   235→
   236→Every paginated endpoint enforces `limit` with `z.coerce.number().int().min(1).max(200)`.
   237→A client cannot request `?limit=1000000` to OOM the function — Zod rejects
   238→it with 400. The default is 50.
   239→
   240→### 2.4 Parameterized queries (no SQL injection)
   241→
   242→ATLAS uses Prisma 6 exclusively. Prisma's query builder always
   243→parameterizes — there is no string concatenation of SQL anywhere in the
   244→codebase. Even the substring search `where: { name: { contains: q } }`
   245→becomes a parameterized `LIKE ?` query under the hood.
   246→
   247→There are no raw SQL queries (`$queryRaw` / `$executeRaw`) anywhere in
   248→`src/app/api/`. The injection surface through SQL is zero.
   249→
   250→### 2.5 No `dangerouslySetInnerHTML` in the frontend
   251→
   252→Verified by reading every file under `src/components/atlas/`. The Reports
   253→view — the only place that renders user-controlled content (the report
   254→`content` field) — uses a `<pre>` block with a JSX text child:
   255→
   256→```tsx
   257→<pre className="...">
   258→  {openReport?.content ?? "(no content)"}
   259→</pre>
   260→```
   261→
   262→React escapes text children. The HTML-format report content (which
   263→includes `<doctype html>...<script>`-free templates) is rendered as plain
   264→text. An attacker who somehow injected HTML into a report would see their
   265→payload displayed as text in the dialog, not executed.
   266→
   267→The HTML report *template* server-side does HTML-escape the title and
   268→`details` (`<`, `>`, `&` → entities). Other fields come from the seed
   269→data, not user input.
   270→
   271→### 2.6 Same-origin, no CORS
   272→
   273→All API endpoints live under `/api/*` on the same origin as the dashboard.
   274→No `Access-Control-Allow-Origin` header is set. The browser's default
   275→same-origin policy blocks any other origin from reading responses.
   276→
   277→### 2.7 Local-only API keys
   278→
   279→The Settings → API keys UI stores keys in `localStorage` under
   280→`atlas:api-keys`. The component's comment is explicit:
   281→
   282→```tsx
   283→<p className="text-xs text-muted-foreground">
   284→  Keys are stored only in your browser&apos;s local storage. They are never sent to the server.
   285→</p>
   286→```
   287→
   288→The keys are never read by any other component, never sent in any fetch
   289→header, and never appear in any network request. They are a mock UI for a
   290→future auth integration.
   291→
   292→### 2.8 No filesystem write surface in the API
   293→
   294→The API does not write to the filesystem (the benchmark scripts write to
   295→`/tmp/atlas-1m.csv` but that's a child-process scratch file, not an API
   296→write surface). The export endpoint streams the response body; it doesn't
   297→write a file to disk.
   298→
   299→### 2.9 Prisma `onDelete: Cascade`
   300→
   301→All child relations (`Tool`, `Capability`, `BenchmarkRun`, `Limit`) cascade
   302→on `Environment` deletion. This prevents orphaned rows when an environment
   303→is deleted. The seed's `deleteMany` in the inverse order (reports → runs →
   304→benchmarks → limits → capabilities → tools → environment) ensures no FK
   305→constraint is violated during re-seed.

   309→## 3. Security headers (recommendation, not yet implemented)
   310→
   311→The current `next.config.ts` does not set security headers. The
   312→recommended set (see `docs/deployment-guide.md` §5 for the full code) is:
   313→
   314→| Header | Value | Why |
   315→|--------|-------|-----|
   316→| `X-Frame-Options` | `DENY` | Prevents the dashboard from being framed (clickjacking). |
   317→| `X-Content-Type-Options` | `nosniff` | Prevents the browser from MIME-sniffing a response as a different content type. |
   318→| `Referrer-Policy` | `strict-origin-when-cross-origin` | Sends the origin (not the full URL) on cross-origin requests; nothing on downgrade. |
   319→| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | Disables device APIs the dashboard doesn't use. |
   320→| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'none';` | Restricts every fetch to the same origin; allows inline scripts/styles (Tailwind needs them); blocks embedding. |
   321→
   322→The CSP includes `'unsafe-inline'` for `script-src` and `style-src` because
   323→Next.js's runtime injects inline scripts (the hydration data, the
   324→`__next_f` chunks) and Tailwind injects inline styles. A future
   325→hardening would use nonce-based CSP, which requires configuring Next.js
   326→with a `nonce` per request.
   327→
   328→For self-hosted deployments with Caddy, the same headers should be set in
   329→the `Caddyfile`'s `header` block.

   333→## 4. Authentication architecture (gap + plan)
   334→
   335→### 4.1 The current state
   336→
   337→ATLAS v1 has **no authentication**. The decision is documented in
   338→`docs/decisions/adr-06-no-auth-v1.md`. The reasons:
   339→
   340→- ATLAS is a read-heavy internal dashboard. The data is non-sensitive
   341→  telemetry about a sandbox host.
   342→- The primary use case is one user (the developer / agent) looking at
   343→  their own environment's data.
   344→- Adding auth adds complexity (login page, session management, token
   345→  rotation, role checks) without proportionate value for v1.
   346→
   347→### 4.2 The plan
   348→
   349→`next-auth` is already in `package.json` (`"next-auth": "^4.24.11"`) but
   350→not wired. The plan for v2:
   351→
   352→1. **Provider: GitHub OAuth**. The repo is on GitHub (`AutomatedLabor/atlas`);
   353→   the dashboard's primary users are GitHub-authenticated developers.
   354→   Configure `NEXTAUTH_SECRET` (random 32-byte hex), `NEXTAUTH_URL` (the
   355→   deployment URL), `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`.
   356→2. **Provider: API key (Credentials)**. For agents / scripts that want to
   357→   hit the API without a browser, accept a long-lived API key in the
   358→   `Authorization: Bearer <key>` header. Validate against a `ApiKey` table
   359→   (new Prisma model) or a static env var list.
   360→3. **Middleware**. A Next.js middleware (`src/middleware.ts`) intercepts
   361→   every `/api/*` request and checks for a valid session or API key.
   362→   - **GET endpoints** require either a session OR an API key.
   363→   - **POST endpoints** require an API key (no browser-only session).
   364→4. **Public read path**. If the dashboard should remain fully public for
   365→   read-only access, leave `GET /api/*` open and only protect POST.
   366→5. **Audit log**. Log every POST to a new `AuditLog` table: timestamp,
   367→   user id, endpoint, request body shape (not full content), response
   368→   status.
   369→
   370→### 4.3 Why not just hide the URL
   371→
   372→URL obfuscation is not authentication. A Vercel preview URL is public,
   373→indexable, and guessable. The dashboard's content (kernel version, public
   374→IP) is the same data a port scanner would see in seconds. Hiding the URL
   375→provides zero real security.
   376→
   377→### 4.4 What auth does NOT solve
   378→
   379→Auth gates access but does not protect against:
   380→
   381→- A logged-in user who runs 1000 benchmarks/sec (still need rate limiting).
   382→- A logged-in user who exports 100 GB of data (still need export limits).
   383→- A logged-in user who creates 10,000 reports (still need write rate
   384→  limits on `POST /api/reports`).
   385→
   386→The full hardening stack is auth + rate limiting + per-user quotas +
   387→audit logs. ATLAS v1 has none of these; the plan adds auth first, rate
   388→limiting second, quotas third.

   392→## 5. Data protection
   393→
   394→### 5.1 No PII
   395→
   396→ATLAS does not collect, store, or display any personally identifiable
   397→information. The "user" of the dashboard is implicit (whoever opened the
   398→URL). The Settings → API keys feature stores keys in `localStorage`, but
   399→the keys are user-supplied labels and values — ATLAS does not generate or
   400→assign them.
   401→
   402→### 5.2 The exposed egress IP
   403→
   404→The seed data includes `publicIp: '8.212.10.159'` and the Limits view
   405→displays it. The footer also shows the hostname and public IP. This is
   406→**intentional**: the entire purpose of ATLAS is to surface the
   407→environment's characteristics, and the public IP is one of them. The IP is
   408→also published in `docs/environment/05-network.md` (publicly readable in
   409→the repo). Hiding it in the dashboard would not protect it.
   410→
   411→### 5.3 The exposed kernel version, CPU model, and limits
   412→
   413→Same reasoning. `Environment.kernel`, `Environment.cpuModel`,
   414→`Limit.limitValue` ("4100 MB", "0 MB swap", "kata-container (KVM)") are
   415→all displayed. They are also all in `docs/environment/`. Hiding them in
   416→the dashboard would not protect them.
   417→
   418→### 5.4 Transport security
   419→
   420→In dev: HTTP (no TLS) on `localhost:3000` (or `:81` via Caddy). For local
   421→development this is fine.
   422→
   423→In prod (Vercel): HTTPS with auto-renewed TLS certificates. Vercel
   424→enforces HTTPS by default; the `https://atlas.yourdomain.com` URL is
   425→served only over TLS.
   426→
   427→For self-hosted with Caddy: enable automatic HTTPS by configuring a
   428→domain in the `Caddyfile` (Caddy provisions TLS via Let's Encrypt
   429→automatically).
   430→
   431→### 5.5 Database at rest
   432→
   433→Dev: SQLite at `db/custom.db` — no encryption at rest. Anyone with read
   434→access to the dev machine can read the DB file. The data is non-sensitive
   435→(the same data is in `docs/environment/` in the public repo).
   436→
   437→Prod (Postgres): the provider (Vercel Postgres, Neon, Supabase) encrypts
   438→at rest by default. Check the provider's documentation for KMS details.

   442→## 6. Incident response
   443→
   444→### 6.1 The benchmark hangs (subprocess doesn't return)
   445→
   446→The 30-second `execFile` timeout will kill the subprocess. The route
   447→returns 500 `benchmark_execution_failed` with the stderr attached.
   448→
   449→If the subprocess keeps hanging on every request:
   450→
   451→1. Check the dev.log / server.log for stderr output from the Python
   452→   process.
   453→2. Check the host's CPU and memory with `top` / `htop` / `free -h`.
   454→3. If the host is genuinely overloaded, restart the Node process (`pkill
   455→   -f "next dev"` then `bun run dev`).
   456→4. If a specific benchmark always hangs, the script itself is broken.
   457→   Inspect `BENCH_PYTHON[name]` in
   458→   `src/app/api/benchmarks/run/route.ts`.
   459→5. If the script needs more than 30 s, raise the timeout in the route (not
   460→   recommended; better to fix the script).
   461→
   462→### 6.2 The database corrupts (SQLite)
   463→
   464→Symptoms: every endpoint returns 500 with `details` mentioning "database
   465→disk image is malformed" or "database is locked".
   466→
   467→1. Stop the dev server: `pkill -f "next dev"`.
   468→2. Back up the corrupt file: `cp db/custom.db db/custom.db.corrupt.$(date +%s)`.
   469→3. Delete and re-push: `rm db/custom.db && bun run db:push`.
   470→4. Re-seed: `bun run prisma/seed.ts`.
   471→5. Restart: `bun run dev`.
   472→
   473→**Caveat**: any user-generated reports or additional benchmark runs
   474→created after the last seed are lost. There is no incremental backup. If
   475→the data matters, snapshot `db/custom.db` regularly.
   476→
   477→### 6.3 The Vercel deploy breaks
   478→
   479→Symptoms: the production URL returns 500, or a specific view shows an
   480→error state.
   481→
   482→1. **Check Vercel dashboard → Deployments** for the most recent deploy
   483→   status. If the build itself failed, the previous deploy is still live.
   484→2. **Rollback**: Vercel → Deployments → click the `⋯` next to the last
   485→   known-good deploy → "Instant Rollback". The prod alias switches to the
   486→   previous build in seconds.
   487→3. **Investigate**: read the build log of the broken deploy. The most
   488→   common causes are: env var drift (e.g., `DATABASE_URL` not set on the
   489→   preview env), a Prisma schema mismatch (the prod DB has a different
   490→   schema than the code expects), or a TypeScript error that
   491→   `next.config.ts`'s `ignoreBuildErrors: true` let through (run
   492→   `bunx tsc --noEmit` locally to catch this).
   493→4. **Fix forward**: commit the fix, push, let Vercel auto-deploy.
   494→
   495→### 6.4 A vulnerability is reported
   496→
   497→If you receive a vulnerability report:
   498→
   499→1. **Do not file a public GitHub issue.** Email the maintainer directly or
   500→   use GitHub's private vulnerability reporting.
   501→2. **Confirm reproduction** on a fresh clone + seed.
   502→3. **Triage severity** using the asset/threat tables in this document.
   503→4. **Patch in a private branch** if the fix is non-trivial; coordinate a
   504→   simultaneous disclosure and release.
   505→5. **Tag a security release** (`vX.Y.Z+1`) and document the CVE in the
   506→   release notes.
   507→
   508→### 6.5 Suspected dependency compromise (supply chain attack)
   509→
   510→Symptoms: a popular ATLAS dependency ships a malicious version (e.g., the
   511→2024 `ulid` or `event-source-polyfill` incidents).
   512→
   513→1. Identify the package and its last known-good version.
   514→2. Pin it in `package.json` to the last known-good version:
   515→   `"package": "1.2.3"` (no `^`).
   516→3. Run `bun install` to update the lockfile.
   517→4. Run `bun audit` to confirm no known CVE remains.
   518→5. Push and redeploy.
   519→6. Audit the application for any unexpected behavior during the window of
   520→   compromise (check Vercel function logs for unexpected outbound
   521→   requests).

   525→## 7. Dependency audit
   526→
   527→### 7.1 Current audit state
   528→
   529→The project does not currently run `bun audit` in CI. To run it manually:
   530→
   531→```bash
   532→bun audit
   533→# (or `npm audit --omit=dev` if you prefer)
   534→```
   535→
   536→`bun audit` queries the npm registry's advisory database and reports any
   537→installed packages with known vulnerabilities. As of v1.0, the project
   538→uses mainstream, well-maintained packages:
   539→
   540→| Package | Risk | Notes |
   541→|---------|------|-------|
   542→| `next` 16 | low | Actively maintained by Vercel. |
   543→| `react` 19 | low | Meta-maintained. |
   544→| `@prisma/client` 6 | low | Prisma team-maintained. |
   545→| `@tanstack/react-query` 5 | low | TanStack team-maintained. |
   546→| `recharts` 2 | low | Open-source, popular. |
   547→| `framer-motion` 12 | low | Framer team-maintained. |
   548→| `lucide-react` | low | Open-source icon set. |
   549→| `next-themes` | low | Small, popular, low surface. |
   550→| `sonner` | low | Toast library. |
   551→| `zod` 4 | low | Popular validation library. |
   552→| `zustand` 5 | low | Small, popular. |
   553→| `next-auth` 4 | medium | Not currently used; installed for v2 auth. Remove if not needed. |
   554→| `z-ai-web-dev-sdk` | unknown | Third-party SDK; not currently imported by ATLAS code; consider removing. |
   555→| `react-syntax-highlighter` | medium | Not currently imported by ATLAS code; consider removing. |
   556→| `@mdxeditor/editor` | medium | Not currently imported by ATLAS code; consider removing. |
   557→| `@dnd-kit/*` | low | Not currently imported; consider removing. |
   558→| `sharp` 0.34 | medium | Native binding; not currently used; consider removing if no image pipeline. |
   559→| `react-day-picker`, `react-resizable-panels`, `input-otp`, `embla-carousel-react`, `@reactuses/core` | low | Optional; not all imported. |
   560→
   561→**Cleanup opportunity**: `package.json` carries several dependencies that
   562→ATLAS doesn't actually import (e.g., `z-ai-web-dev-sdk`, `react-syntax-highlighter`,
   563→`@mdxeditor/editor`, `@dnd-kit/*`, `sharp`). Removing the unused ones
   564→shrinks the install, reduces the supply-chain attack surface, and speeds
   565→up `bun install`.
   566→
   567→### 7.2 Proposed CI audit gate
   568→
   569→```yaml
   570→# .github/workflows/audit.yml (proposed)
   571→name: Audit
   572→on: { schedule: [{ cron: "0 0 * * *" }], workflow_dispatch: {} }
   573→jobs:
   574→  audit:
   575→    runs-on: ubuntu-latest
   576→    steps:
   577→      - uses: actions/checkout@v4
   578→      - uses: oven-sh/setup-bun@v1
   579→      - run: bun install --frozen-lockfile
   580→      - run: bun audit
   581→```
   582→
   583→A daily audit run catches newly disclosed CVEs. Pair with a Dependabot
   584→config (`/.github/dependabot.yml`) for automated PRs that bump versions.

   588→## 8. Compliance notes
   589→
   590→ATLAS is an internal tool that does not process PII, payment data, health
   591→data, or any other regulated data category. None of the following
   592→frameworks apply to ATLAS v1 as built:
   593→
   594→- **GDPR**: no personal data is collected. The Settings → API keys feature
   595→  stores user-supplied data in `localStorage`, which is under the user's
   596→  control and never sent to the server.
   597→- **CCPA**: same.
   598→- **HIPAA**: no health data.
   599→- **PCI-DSS**: no payment data.
   600→- **SOC 2**: ATLAS is not a SaaS providing services to other businesses;
   601→  SOC 2 is not applicable.
   602→- **ISO 27001**: ATLAS does not claim certification; the security measures
   603→  above are voluntarily documented.
   604→
   605→If ATLAS evolves to handle user-provided environments (multi-tenant) or
   606→store credentials for external systems, this section will need to be
   607→re-evaluated.
