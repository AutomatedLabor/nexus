# 10. JIT Correctness Proof Outline

## Theorem statement

**Theorem (JIT Correctness).**  The Aether JIT compiler (planned
for v3) produces JIT-compiled code that, when executed, produces
the same observable behavior as the VM on the same bytecode.
Deoptimization (when the JIT'd code's assumptions fail) restores
the VM state correctly and resumes execution in the VM without
observably changing the program's behavior.

Formally: for any verified bytecode module `M` and any starting
state `s`:

- If the JIT compiles `M` to native code `J` (under assumptions
  `A`), and `J` executes without violating `A`, then
  `run(J, ~s) ~ run(VM, s)` (the JIT'd code produces the same
  output as the VM).
- If `J`'s assumptions `A` are violated at runtime, the JIT
  deoptimizes (restores the VM state) and resumes in the VM.  The
  observable behavior is the same as if the JIT had not been
  invoked.

## Background: the JIT

The JIT (planned for v3) compiles "hot" bytecode (functions that
are called frequently) to native code, with optimistic
assumptions:

- The receiver's type is the most-observed type (type
  specialization).
- The call target is the most-observed target (inline caching).
- The loop's iteration count is bounded (for loop unrolling).

If the assumptions hold, the JIT'd code runs faster than the VM.
If the assumptions fail, the JIT deoptimizes:

1. The JIT'd code detects the failure (e.g., a type mismatch).
2. The JIT'd code transfers control to a deoptimization handler.
3. The deoptimization handler reconstructs the VM's state from
   the JIT'd state.
4. The VM resumes execution from the corresponding bytecode
   instruction.

## Proof outline

### Step 1: The semantic correspondence

We extend the `~` relation from `09-native-codegen-correctness.md`
to include the JIT's state:

- `VM.pc ~ JIT.rip` (instruction pointers correspond).
- `VM.regs[i] ~ JIT.mem[frame_base + i * 8]` (VM registers in
  native memory).
- `VM.upvalues[i] ~ JIT.mem[upvalue_base + i * 8]` (upvalues).
- `VM.stack ~ JIT.stack` (call stacks).

The JIT's state has additional fields (the assumptions `A`, the
optimization metadata), but these are not part of the observable
state.

### Step 2: JIT compilation correctness

For each bytecode instruction `instr`, the JIT compiles to native
code `J(instr)` (with assumptions `A`).

**Lemma (JIT-Instruction-Compilation).**  If the VM in state `s`
executes `instr` and transitions to `s′`, and the JIT's
assumptions `A` hold in `s`, and the JIT in state `~s` executes
`J(instr)` and transitions to `~s″`, then `~s′ = ~s″` (the
resulting states correspond).

Proof: by case analysis on `instr.op`, similar to
Instruction-Compilation in `09`.  The JIT's code is similar to the
AOT codegen's code, but with optimistic assumptions:

- For `Call`, the JIT may inline the call target (assumption: the
  target is the most-observed one).  If the target matches, the
  inlined code executes; otherwise, deopt.
- For `LoadField`, the JIT may use a fixed offset (assumption: the
  object's shape is the most-observed one).  If the shape matches,
  the offset is correct; otherwise, deopt.
- For `Add`, the JIT may specialize for int (assumption: both
  operands are int).  If both are int, the int addition executes;
  otherwise, deopt.

When the assumptions hold, the JIT's code produces the same
effect as the VM.  ✓.

### Step 3: Deoptimization correctness

When an assumption fails, the JIT deoptimizes.  The deopt process:

1. The JIT'd code detects the failure (e.g., a type-check
   instruction fails).
2. The JIT'd code transfers control to a deopt handler (a piece
   of native code generated by the JIT).
3. The deopt handler reconstructs the VM's state from the JIT's
   state:
   - The VM's `pc` is set to the bytecode instruction
     corresponding to the JIT'd instruction that deoptimized.
   - The VM's `regs` are filled in from the JIT's registers (and
     from the deopt metadata, which records where each VM register
     is stored in the JIT's state).
   - The VM's `upvalues` and `stack` are restored similarly.
4. The VM resumes execution from the reconstructed state.

**Lemma (Deopt-State-Reconstruction).**  The deopt handler
reconstructs a VM state `s′` that corresponds to the JIT's state
`~s` at the deopt point: `s′ ~ ~s`.

Proof: the deopt metadata (generated by the JIT at compile time)
records the mapping from JIT state to VM state.  The deopt
handler uses this metadata to fill in the VM's state.  By the
mapping's correctness (the metadata is generated by the JIT's
own analysis, which is sound), the reconstructed state `s′` is
the state the VM would have been in if it had executed the
bytecode up to the deopt point.  ✓.

**Lemma (Deopt-Resumption).**  After deopt, the VM resumes
execution from `s′` and produces the same observable behavior as
if the JIT had not been invoked.

Proof: by Deopt-State-Reconstruction, the VM's state `s′` is the
state the VM would have been in.  The VM resumes execution from
`s′`, following the operational semantics.  The observable
behavior is the same as if the JIT had not been invoked (the JIT
is invisible to the program).  ✓.

### Step 4: Whole-program correctness

**Theorem (JIT-Whole-Program-Correctness).**  For any well-typed
Aether program `P`, `run(treewalker(P)) = run(JIT(P))` (modulo
performance).

Proof:

- The VM executes `P`'s bytecode.  For each function, the JIT
  compiles it (under assumptions `A`) when it becomes hot.
- While `A` holds, the JIT'd code produces the same output as the
  VM (by JIT-Instruction-Compilation, inductively).
- When `A` fails, the JIT deoptimizes (by Deopt-Resumption), and
  the VM resumes.  The observable behavior is preserved.
- The composition (JIT for hot paths, VM for cold paths, deopt
  for assumption failures) produces the same output as the pure
  VM.  ✓.

### Step 5: Deopt safety

**Theorem (Deopt-Safety).**  Deoptimization never loses state
(no VM register is dropped) and never duplicates state (no VM
register is double-counted).

Proof:

- No loss: the deopt metadata records the location of every VM
  register in the JIT's state.  The deopt handler reads each
  location and writes to the corresponding VM register.  So no
  VM register is dropped.  ✓.
- No duplication: each VM register has exactly one location in
  the JIT's state (the metadata is a function, not a relation).
  So no VM register is double-counted.  ✓.

### Step 6: Termination of deopt

**Lemma (Deopt-Termination).**  The deopt handler terminates.

Proof: the deopt handler is a fixed sequence of native
instructions (read each JIT location, write to the corresponding
VM register, jump to the VM's resume point).  The number of
instructions is bounded by the number of VM registers (which is
bounded by `nlocals`, a function property).  So the deopt handler
terminates.  ✓.

## Assumptions

1. The JIT's assumptions are correctly identified (the type
   analysis, inline cache, etc., are sound).
2. The JIT's code is correctly generated (the per-instruction
   templates match the VM's semantics when the assumptions
   hold).
3. The deopt metadata is correctly generated (the mapping from
   JIT state to VM state is sound).
4. The deopt handler is correctly implemented (it reads the
   metadata and reconstructs the VM state).
5. The hardware is correct (assumed).
6. The VM is correct (proven in `09` and `bytecode-verifier.md`).

## Key lemmas

1. **JIT-Instruction-Compilation**: each JIT'd instruction
   matches the VM's effect (when assumptions hold).
2. **Deopt-State-Reconstruction**: the deopt handler
   reconstructs the correct VM state.
3. **Deopt-Resumption**: after deopt, the VM produces the same
   behavior as without the JIT.
4. **Deopt-Safety**: deopt loses no state and duplicates no
   state.
5. **Deopt-Termination**: the deopt handler terminates.
6. **JIT-Whole-Program-Correctness**: the JIT'd program produces
   the same output as the pure VM.

## What's mechanized vs hand-waved

- **Mechanized** (in future Coq/Lean work): the per-instruction
  JIT compilation proof (similar to `09`), the deopt state
  reconstruction (a mapping), the deopt safety (no-loss, no-
  duplication).  Estimated Coq effort: ~15000 lines.
- **Hand-waved**: the JIT's assumption analysis (depends on
  profile data, which is statistical).  The deopt metadata's
  correctness (assumed by the JIT's analysis).  The deopt
  handler's implementation (depends on the runtime).

## Conclusion

JIT correctness is the guarantee that the JIT'd code produces
the same output as the VM, with deoptimization handling
assumption failures.  The proof reduces to:

1. JIT-Instruction-Compilation: each JIT'd instruction matches
   the VM's effect (when assumptions hold).
2. Deopt-State-Reconstruction: deopt reconstructs the correct VM
   state.
3. Deopt-Resumption: after deopt, the VM produces the same
   behavior.
4. Deopt-Safety: deopt loses no state, duplicates no state.
5. Deopt-Termination: deopt terminates.
6. JIT-Whole-Program-Correctness: the whole program's output
   matches.

The proof is paper-style; full mechanization is future work.
The key lemmas are the per-instruction compilation (similar to
`09`) and the deopt state reconstruction (a mapping from JIT
state to VM state, generated by the JIT's analysis).

The v3 plan includes the JIT; the formal proof here establishes
the design's correctness.  The implementation will follow the
design, with the deopt metadata generated at JIT compile time
and the deopt handler implemented as a runtime support function.

Together with the type-safety proofs (`01`, `02`), the IR
equivalence proof (`08`), and the native codegen correctness
(`09`), JIT correctness ensures that Aether programs produce the
same output regardless of the execution strategy (tree-walker,
VM, native AOT, or JIT).
